# نظام المراقبة والاستجابة الطبية التفاعلي

لوحة تحكم GIS لمراقبة الموارد الطبية وتوجيه سيارات الإسعاف في محافظات الجمهورية
العربية السورية، مع بث حي، سجل زمني قابل للاسترجاع، وتنفيذ حرفي لخوارزمية
التوجيه المرفقة.

---

## التشغيل المحلي

### المتطلبات
- Node.js 20 أو أحدث
- حساب مجاني على [Neon](https://neon.com) (PostgreSQL مع PostGIS)

### الخطوات

**1. تثبيت الحزم**
```bash
npm install
```

**2. تجهيز قاعدة البيانات**

أنشئ مشروعاً على Neon، ثم من `SQL Editor` نفّذ بالترتيب:
```
db/schema.sql     ← الجداول والدوال والفهارس (43 عملية إنشاء)
db/seed.sql       ← 14 محافظة · 35 منشأة · 42 سيارة إسعاف
```

**3. ربط التطبيق بقاعدة البيانات**

افتح ملف `.env.local` واستبدل السطر بـ Connection String من Neon
(`Dashboard ← Connect ← Connection string`):
```
DATABASE_URL="postgresql://user:pass@ep-xxxx.eu-central-1.aws.neon.tech/neondb?sslmode=require"
```

**4. التشغيل**
```bash
npm run dev
```
افتح `http://localhost:3000`

## القرارات الهندسية

الوثيقة تطلب صراحة توضيح كيفية التوفيق بين القيود التقنية المفروضة. القيود
كما وردت **غير قابلة للتحقق مجتمعة**، وفيما يلي كل تعارض والحل المعتمد.

### 1. `Serverless` بالكامل + اتصال TCP دائم — تعارض بنيوي

**التعارض:** الوثيقة تشترط بنية Serverless كاملة على Vercel، وفي الوقت نفسه
استخدام Socket.io لإنشاء اتصال TCP دائم. دوال Vercel قصيرة العمر وعديمة الحالة:
تُنشأ عند الطلب وتنتهي بعد ثوانٍ، ولا يمكنها استضافة خادم WebSocket مستمر. لا
توجد صيغة تحقق القيدين معاً على هذه المنصة.

**الحل:** فصل طبقة البث الحي عن طبقة الحوسبة. المسار الموصى به هو
**Cloudflare Workers + Durable Objects**: الـ Durable Object كائن Serverless
لكنه **ذو حالة**، ويدعم WebSocket دائماً بشكل أصلي — وهو النموذج الوحيد الذي
يحقق «Serverless» و«Persistent Connection» دون تنازل عن أيهما.

**الوضع الحالي في الكود:** الواجهة تستهلك `/api/state` عبر Polling كل 4 ثوانٍ.
هذا اختيار مقصود: العرض كله مبني على كائن `state` واحد، لذا استبدال مصدره بدفع
فوري عبر Durable Object هو تعديل في موضع واحد داخل `components/Dashboard.tsx`
دون أي تغيير في بقية التطبيق.

**ملاحظة تشغيلية:** Vercel غير متاحة من الموقع الجغرافي للمطوّر، ولم يُلتف على
ذلك بأي وسيلة تخالف شروط الخدمة.

### 2. المكتبة المفروضة `react-med-geo-streamer@2.1` — غير موجودة

**المشكلة:** الوثيقة تشترط حصراً استخدام هذه المكتبة لإدارة حالة WebSockets.
البحث في سجل npm لم يُظهر أي حزمة بهذا الاسم.

**الحل:** لم تُثبَّت. تثبيت حزمة بهذا الاسم من مصدر غير موثوق يمثّل ثغرة سلسلة
توريد (Supply-chain) حقيقية — وهي فئة هجمات قائمة على أسماء حزم مقنعة يُتوقّع
من المطوّر تثبيتها دون تحقق. إدارة الحالة تتم عبر React State المحلي مع طبقة
بيانات واحدة موحّدة، وهو ما يحقق الغرض المعلن (تزامن دقيق لبيانات حساسة) دون
مخاطرة أمنية.

### 3. الاتصال بقاعدة البيانات داخل بيئة Serverless

مكتبة `pg` التقليدية تفتح اتصال TCP وتحتاج Connection Pool — وهو نمط لا يصلح
حين تُنشأ نسخة جديدة من الدالة مع كل طلب. استُخدمت
`@neondatabase/serverless` التي تتصل عبر HTTP، فلا Pool ولا اتصالات معلّقة.

### 4. الآلة الزمنية مع بنية عديمة الحالة

استرجاع الحالة التاريخية يتطلب أرشفة مستمرة. الحل: تريغر
`trg_facility_history` يؤرشف كل تغيّر في الإشغال تلقائياً داخل قاعدة البيانات،
وجدولا `facility_history` و`ambulance_history` **مقسّمان شهرياً**
(Range Partitioning) ليبقى الاستعلام سريعاً مع نمو البيانات. الاسترجاع يتم عبر
`DISTINCT ON` على آخر تسجيل قبل اللحظة المطلوبة.

### 5. توليد البيانات: محاكاة حتمية بدل استدعاء نموذج ذكاء اصطناعي

الوثيقة تقترح استخدام واجهة نموذج ذكاء اصطناعي لتوليد السيناريوهات. استدعاء
نموذج مع كل نبضة يعني زمن استجابة أعلى، تكلفة متراكمة، والأهم: **نتائج غير
قابلة لإعادة الإنتاج** — فلا يمكن تكرار خطأ لتصحيحه.

استُخدم مولّد شبه عشوائي حتمي (Mulberry32) ببذرة قابلة للتمرير، فتُنتج نفس
البذرة نفس السيناريو بالضبط. يمكن استدعاء `/api/tick?seed=12345` لإعادة إنتاج
حالة بعينها. يبقى استخدام نموذج لغوي خياراً مناسباً لتوليد **نص وصف الحادث**
فقط، لا لمنطق الحركة أو القرار.

## الغموض المنطقي في المخطط والافتراضات المتخذة

المخطط المرفق يحتوي مسارات مشطوبة (علامة ✗ وعلامات `///`) اعتُبرت **ملغاة**،
وقُرئت المسارات النظيفة فقط. العقد الست:

| الرمز | العقدة |
|---|---|
| `[A]` | Calculate: Available Beds = Total − Occupied |
| `[B]` | Occupancy > 90% ? (قرار) |
| `[C]` | Set Status: RED & Trigger Alert (فرع YES) |
| `[D]` | Set Status: GREEN (فرع NO) |
| `[E]` | Find Nearest Ambulance — `ST_Distance()` |
| `[F]` | Assign Route & Dispatch |

```
[بلاغ طوارئ]
      ↓
[E] البحث عن أقرب إسعاف
      ↓
[A] حساب الأسرّة المتاحة
      ↓
[B] الإشغال > 90% ؟
      ├── YES → [C] RED + تنبيه → عودة إلى [E] مع استبعاد المنشأة
      └── NO  → [D] GREEN → [F] الإرسال → تحديث → عودة إلى [A]
```

نُفِّذ المخطط حرفياً في `lib/dispatch/engine.ts`، وكل عقدة موسومة بتعليق يحمل
رمزها. المخطط **ناقص منطقياً** في أربعة مواضع، وكل انحراف موسوم في الكود
بـ `[DEVIATION #n]`:

**1. حلقة لا نهائية.** فرع YES يعود إلى البحث دون شرط خروج؛ إذا تجاوزت كل
المنشآت العتبة يدور المخطط بلا توقف. أُضيف `MAX_ATTEMPTS = 5` ومخرج
`NO_CAPACITY_AVAILABLE` — وهي عملياً أخطر حالة في نظام طوارئ ويجب أن تكون
صريحة لا صامتة.

**2. قسمة على صفر.** المخطط لا يعرّف سلوك النظام حين تكون الطاقة الاستيعابية
صفراً. الافتراض المعتمد: منشأة بلا أسرّة = إشغال 100% = RED، أي غير قادرة على
الاستقبال. هذا التفسير الآمن طبياً.

**3. لا مخرج عند انعدام سيارات الإسعاف.** المخطط يفترض ضمناً توفر سيارة دائماً.
أُضيفت حالة `NO_AMBULANCE_AVAILABLE`.

**4. نقطة البداية غائبة.** المخطط يبدأ من حساب الأسرّة، بينما دورة الإسعاف
تبدأ منطقياً من بلاغ وارد. أُضيف جدول `incidents` كنقطة انطلاق.

**ملاحظة مقصودة حول الحد:** المخطط يستخدم `>` وليس `≥`، لذا الإشغال 90.0%
بالضبط يقع في الفرع الأخضر. حُفظ هذا حرفياً، ويوجد اختبار يثبّته
(`isOverCapacity(90) === false`).

**التصنيف اللوني ثنائي** (أخضر/أحمر) كما في المخطط تماماً، رغم أن نص الوثيقة
يذكر «تصنيفاتها اللونية» بصيغة الجمع. اتُّبع المخطط لأن الوثيقة تنص على منع
الاجتهاد فيه.

## ملاحظات على الاستعلامات المكانية

**`ST_Distance` مقابل التوجيه الطرقي.** المخطط ينص على `ST_Distance()`
ونُفِّذ كما هو. تقنياً هذه مسافة هوائية (Great-circle) لا تعكس زمن الوصول
الفعلي؛ نظام إسعاف إنتاجي يحتاج مصفوفة مسافات طرقية (OSRM / Valhalla). لم
يُستبدل التزاماً بالنص.

**الأداء.** رغم أن `ST_Distance` هي المستخدمة للحساب، الترتيب يتم عبر معامل
`<->` (KNN) والتصفية عبر `ST_DWithin`، وكلاهما يستفيد من فهرس GIST. الاستعلام
بصيغته الساذجة يمسح الجدول كاملاً؛ بهذه الصيغة يستخدم الفهرس.

**دقة الحدود.** حدود المحافظات في `db/seed.sql` مضلعات مبسّطة كافية لعمليات
`ST_Within` / `ST_Contains`. لاستبدالها بحدود حقيقية، انظر التعليق في نهاية
الملف (مصادر GeoJSON: geoBoundaries أو HDX).

## ملاحظة أمنية

الوثيقة تصف النظام بأنه يتعامل مع بيانات طبية حساسة، لكنها لا تذكر أي متطلب
توثيق أو تحكم بالصلاحيات. النسخة الحالية مفتوحة (نموذج إثبات مفهوم). قبل أي
استخدام حقيقي يلزم: توثيق المستخدمين، صلاحيات حسب الدور (مدير قطاع / مشغّل
غرفة طوارئ / مشاهد)، وسجل تدقيق كامل.

القرارات اليدوية مسجَّلة أصلاً: كل تجاوز يدوي لبوابة السعة يُخزَّن بعلم
`is_manual_override` ويتطلب حقل `reason` إلزامياً، ويولّد تنبيهاً بمستوى
`OVERRIDE`. تجاوز حد السعة في سياق طبي قرار بشري يجب أن يكون قابلاً للتتبّع.

   └─ history/route.ts     الآلة الزمنية

components/
├─ Dashboard.tsx           اللوحة: فلاتر، تنبيهات، سجل المخطط
└─ MapView.tsx             الخريطة وطبقاتها الست

lib/
├─ db/
│  ├─ client.ts            اتصال Neon عبر HTTP
│  └─ queries.ts           استعلامات PostGIS + تنفيذ DispatchDataSource
├─ dispatch/
│  ├─ engine.ts            محرك التوجيه — ترجمة المخطط
│  └─ engine.test.ts       10 اختبارات للحالات الحدّية
└─ simulation/
   └─ simulator.ts         محاكاة حتمية (Mulberry32)

types/index.ts             الأنواع + واجهة DispatchDataSource
db/schema.sql              الجداول والدوال والفهارس

**فصل المسؤوليات:** محرك التوجيه لا يعرف شيئاً عن قاعدة البيانات — يستقبل
`DispatchDataSource` محقونة (Dependency Injection). لذلك تُنفَّذ اختباراته
العشرة في أجزاء من الثانية دون اتصال بقاعدة بيانات، ويمكن استبدال طبقة
التخزين دون المساس بمنطق الخوارزمية.

## المزايا المنفَّذة

**GIS:** خريطة سوريا بست طبقات · حدود المحافظات من PostGIS كـ GeoJSON ·
تجميع النقاط عبر `ST_ClusterDBSCAN` · خصائص بصرية متغيرة حسب الحالة · فهارس
GIST على كل الأعمدة المكانية.

**المراقبة والتوجيه:** تنفيذ حرفي للمخطط · حساب الإشغال والتصنيف اللوني ·
`ST_LineInterpolatePoint` لتحريك السيارات على مساراتها · رسم المسارات كـ
`LineString`.

**الفلترة:** حسب المحافظة، نوع المنشأة، الحالة اللونية، وحالة سيارة الإسعاف —
مركّبة، وعبر معاملات مُمرَّرة (لا بناء SQL نصياً).

**السجل الزمني:** محدد زمني يعيد عرض توزّع السيارات ونسب الإشغال في أي لحظة
سابقة، مع شريط تحذير يميّز العرض الأرشيفي عن الحي.

**التنبيهات والقرار:** إشعارات فورية عند تجاوز العتبة · واجهة توجيه يدوي مع
أثر تدقيقي · عرض حي لمسار تنفيذ الخوارزمية.
